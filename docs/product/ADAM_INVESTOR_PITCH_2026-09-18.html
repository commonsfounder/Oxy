ADAMInvestor pitch · 10 slides · grounded in PRODUCT / NORTH_STAR / device contract

01 / TITLE

Give it the outcome. It does the legwork.

Adam is a general-purpose personal-AI worker for the household. You state the intended outcome and grant access; Adam composes browser use, connected services, memory, communication, files, long-running work, and verification inside deterministic safety boundaries.

Companion surface: iPhone app — Home / Ask Adam / Activity / Services / Settings.

02 / PROBLEM

Households drown in digital legwork.

  • Shopping, booking, forms, account admin, reminders, subscriptions.
  • Chatbot shells hide every capability behind a composer.
  • Task managers make you operate the queue.
  • Integration catalogues connect accounts but do no work.
  • Smart-home demos fake rooms, presence, sensors.

Nobody wants to operate computers step by step. They want to delegate.

03 / PRODUCT

Home answers four questions.

What does Adam know?
Household state now.
Does anything need me?
Approvals with real context.
What is Adam doing?
Live work + watches.
What changed?
Outcomes, deduplicated.

Ask Adam (voice + text) is a mode, one tap away. Calm, capable, discreet, concrete.

04 / HOW IT WORKS

One runtime, not domain agents.

  • Orchestrator: think → act → observe → adapt, checkpointed.
  • Execution boundary: validate → review gate → invoke → log.
  • Browser as environment: open, observe, fill, checkout.
  • Money guard: spend caps + review-gated payment, amount re-read off the live page.

New task ⇒ no new subsystem. Connectors are real actions or handoff deep-links.

05 / LIVE PROOF

Verified in prod, not demos.

  • Browser agent (most mature): persistent sessions, logins, real live purchases.
  • Appointment booking: choices → explicit approval → booking + calendar + Home confirmation (sandbox).
  • Durable approvals + per-goal sessions with real prod writes.
  • Voice I/O runs; core promise proven via typed chat so far.

Honest gap: some bot-walled sites (Magento/BigCommerce class) have no viable path yet.

06 / SAFETY + TRUTH

Reasoning is probabilistic. Authority is not.

  • Payments, destructive, identity, irreversible actions stay gated at the boundary.
  • "Tool invoked" ≠ done. Success only after state is re-read.
  • Unknown / unavailable / not configured are designed states — never faked.
  • Vault RLS closed and verified both directions; audit history explicit.

07 / WEDGE

Phone first. Hardware earned.

The wedge is the phone + shipped transacting capability: basket, guest checkout, card fill, reauth walls, honest outcome reporting.

A home-device pivot was tested and rejected (Aug 2026): hardware is earned once software demand is undeniable, not the opener.

08 / HARDWARE VISION

North star, deferred by choice.

  • Always-available device, far-field mic, speaker, wake word, physical privacy control, OTA, encryption.
  • Today: iPhone only. Canonical path is runtime → bounded event → authenticated paired browser → ack.
  • XIAO BLE prototypes + ESP32 beacon are experiments — no frozen PCB contract.

Build gates: transport vocabulary, pairing/offline, mic latency, battery/thermal, controls, BOM/antenna, updates, privacy, month-long household proof.

09 / BUSINESS

Work done, not accounts connected.

  • Household worker across shopping, travel, banking visibility, smart home, subscriptions (partly built).
  • Real payment rails with caps + review (Stripe card flow; bank top-up shipped).
  • Trust surfaces — permissions, approvals, audit — as the moat.

Stage: early. Verified single behaviours in prod; next is dependable week-long coverage.

10 / ASK

From verified behaviours to dependable coverage.

  • Week-long watches → Home cards → verified outcomes.
  • Widen ecosystem where real; harden permission coverage.
  • Prove voice end-to-end; graduate one commodity ambient output first.

Ask: capital to turn live single behaviours into household coverage — hardware earned, not opened.
