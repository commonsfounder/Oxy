## Found this session: display-pairing grant drift

`supabase-migration-paired-displays.sql` ends with `revoke all ... from public` and
`grant execute ... to service_role` on `redeem_display_pairing`. Production does not match it:

```
{postgres=X/postgres,anon=X/postgres,authenticated=X/postgres,service_role=X/postgres}
```

A `SECURITY DEFINER` function that pairs a display to the challenge's `user_id` is callable by an
unauthenticated client at `/rest/v1/rpc/redeem_display_pairing`. Supabase grants EXECUTE on public
functions to `anon` and `authenticated` by default, and `create or replace function` preserves an
existing ACL — so a revoke that never ran, or ran before a later replace, leaves nothing in the
file to say it is not in force.

Abuse still needs an unexpired challenge id (a uuid) plus its code hash, so this is **the intended
boundary being absent, not a known break.** The API calls the RPC with the service-key client
(`api/index.js:9266`), so revoking `anon` and `authenticated` does not touch the working path.

`supabase/migrations/supabase-migration-display-pairing-grants.sql` (added here) re-applies it.
**Applied to production** on 2026-08-29 via the Supabase MCP, after the user asked for it. The ACL
went from the line above to `{postgres=X/postgres,service_role=X/postgres}`, and
`has_function_privilege` now answers `anon` false, `authenticated` false, `service_role` true — so
the pairing path, which calls the RPC with the service-key client, is untouched.

Note the gap it exposes: `npm run check:schema` compares declared tables to live tables and does
not read function ACLs. This class of drift is invisible to the deploy gate — the same shape as the
2026-08-24 incident AGENTS.md records, one level down.

  per min` — and all on `user123`. That is the unpaced first stress run `cab109c` describes, not

- **Fixed here — the issue that burst exposed:** a provider 429 was persisted as a terminal `failed` task
  (`agentTrace.status = 'error'` → `TRACE_STATUS_TO_CANONICAL` → `'failed'`), and `last_error` keeps
  the raw provider string. `sanitizeAgentTaskText` strips URLs and emails and truncates to 180
  chars, so what a user would see in their task list is
  `openai 429: { "error": { "message": "Rate limit reached for gpt-5.6-luna in organization
  org-…"`. A TPM limit is retryable and is not a task outcome; only `travel-inventory.js` retries a
  429 today, and nothing did at the chat/brain layer. Test traffic this time, but the mechanism was
  not test-only.

  Provider HTTP failures now throw through one `providerHttpError` helper carrying `status`,
  `rateLimited`, `retryable` and the provider's `Retry-After`, so the loop can tell a rate limit
  from a bad request without reading the message. The in-loop retry honours that hint (bounded at
  5s, and the header itself capped at 60s) instead of a flat 500ms that cannot outlast a per-minute
  limit. When it still fails, the run stops as a new trace status `rate_limited`, which the
  canonical map sends to `paused` — checkpoint intact, `resumable` true — with plain copy instead of
  the provider body. A non-429 keeps the old `error` → `failed` path and its diagnosis, because a
  bad request is this system's bug to fix. `test/smoke/provider-rate-limit.test.js` covers both
  sides, including that no user-visible string carries the org id, the model name, or the envelope.
- Supabase security advisors: 56 tables report `rls_enabled_no_policy` at INFO — expected and safe
  under a service-key backend (no policy plus RLS is deny-by-default for `anon`/`authenticated`).
  Two WARNs: the grant drift above, and a mutable `search_path` on
  `update_travel_sessions_updated_at` (on one of the orphan travel tables).
