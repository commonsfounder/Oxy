## What was fixed

**`7abfe04` — session import could store an identity session.** The refusal list was matched
against the site requested while cookie filtering keeps subdomains, so `accounts.google.com` was
refused but the parent, `google.com`, sailed through — and Google's SSO cookies sit on
`.google.com` itself. Verified against the old code: accepted, 3 cookies stored. Containment is
now checked in both directions, plus a second gate on the cookies that survived the filter.

**`bbc2c3f` — supabase-js returns `{ error }`, it does not throw.** True for RLS refusals,
constraints, and a dead host (`TypeError: fetch failed` arrives as a value). Three call sites read
as safety nets while being unreachable: `authorizeCredentialUse` handed out an uncounted credential
when the use-count write failed, `/health` reported `db: ok` for every failure it exists to detect,
and `DELETE /preferences` returned `success: true` for a delete that never happened.
`notification-delivery.js` already documents a third variant of this, so the pattern now has a home
in `test/smoke/supabase-error-shape.test.js` — add the next call site that gets it wrong there.

**`d1361ac` — task-scoped credential grants authorised nothing.** The bounded permission, and the
DEFAULT scope in `validateGrantInput`. `authorizeCredentialUse` was called with
`session.pendingCredentialTaskId`, only assigned *after* an offer, so the decision always saw null
and always answered `wrong_task`; and the only bindable id was `runOrderingTurnImpl`'s `taskId`, a
fresh `randomUUID()` every turn. Sessions now carry a run-lifetime `credentialTaskId`.
`decideCredentialUse` itself was always correct and is unchanged.

**`9089489` — the permissions had no UI.** Grants and the use log were endpoints only, so the one
thing a person most needs to undo was the one thing they could not see. Vault screen now lists
permissions with a Revoke on each live one, and recent sign-in activity (refusals included — a
denied row is what shows a page steering the agent at a site that was never permitted).

**`7c0813f` — two concurrent runs could spend the same use.** The counter was a
read-modify-write; reproduced against the old code, a grant capped at one sign-in with the cap
already spent still answered `allowed: true, reason: granted`. Now a compare-and-set, with a
bounded retry that re-reads so an uncapped permission keeps working and a capped one gets its
limit re-checked. No migration needed — it is a filter on the update.

## Open, not fixed

- **`VaultView.swift` has never been compiled.** No Swift toolchain in a web container. It was
  written against the components and APIs actually read in the file, and brace/paren balance and
  the absence of SF Symbols were checked mechanically — but **build it in Xcode before shipping**.
  `test/smoke/vault-ios-contract.test.js` guards the JSON seam (selected columns vs. the Swift
  coding keys, not-null vs. non-optional, the sheet's TTLs vs. `MAX_TTL_MINUTES`), which is the
  part that would fail silently across the two build systems.
- **Nothing creates a task-scoped grant yet.** The run identity is now surfaced on the ask
  (`credentialTaskId` on `ready_for_credential_use`, forwarded by `api/actions/browser.js`), so a
  client can offer "allow this for this task" — but no client does. Standing grants are what works
  end to end today, including for scheduled unattended routines.

## Run these on the Mac

A Claude Code **web** session runs in a cloud container, not on the Mac — being sat at the Mac
does not move it. These need a local session (`claude` in the repo) or your own shell:

```sh
git fetch origin && git checkout claude/review-and-capabilities-qlvuso
npm ci
npm test                 # expect 1906/1908; the 89 above only fail without real credentials
npm run check:schema     # the real gate, against the real database
xcodebuild -project OxyApp/OxyApp.xcodeproj -scheme OxyApp -destination 'generic/platform=iOS' build
```

The `xcodebuild` line is the one that matters most: `VaultView.swift` has never been compiled.
